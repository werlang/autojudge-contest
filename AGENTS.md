# AGENTS.md

## Project Scope

- This repository is a VS Code extension for browsing AutoJudge contest data with team credentials.
- The implemented runtime currently covers browser team login (web hand-off), logout, session restore with Loading and Offline states, contest explorer rendering, the contest status bar, generated Markdown pages (contest overview, problem, submission, team details), active-file submission with a confirmation prompt and verdict polling, submission output comparison, public testcase export, and ranked standings refresh.
- The sidebar surface includes `Contest Explorer` and `Standings` under the same `AutoJudge Contest` activity-bar container.
- Keep changes focused on the extension, its docs, and its agent customizations. Do not add unrelated app or backend patterns.

## Working Conventions

- Use modern ESM-style JavaScript consistent with the existing `import` and named export pattern.
- Preserve the current ownership boundaries: activation in [src/extension.js](src/extension.js), command registration in [src/commands/contest-commands.js](src/commands/contest-commands.js), controller flow in [src/controllers/contest-controller.js](src/controllers/contest-controller.js), presentation helpers in [src/presentation/contest-presentation.js](src/presentation/contest-presentation.js), providers in [src/providers/contest-tree-provider.js](src/providers/contest-tree-provider.js), [src/providers/teams-tree-provider.js](src/providers/teams-tree-provider.js), and [src/providers/contest-status-bar.js](src/providers/contest-status-bar.js), remote API helpers in [src/services/contest-api.js](src/services/contest-api.js), session persistence in [src/services/contest-session.js](src/services/contest-session.js) and [src/services/session-store.js](src/services/session-store.js), testcase/workspace helpers in [src/workspace/contest-public-cases.js](src/workspace/contest-public-cases.js) and [src/workspace/contest-submission-workspace.js](src/workspace/contest-submission-workspace.js), generated page and compare-output files in [src/workspace/contest-page-files.js](src/workspace/contest-page-files.js), and neutral shared helpers in [src/utils/](src/utils).
- Prefer maintainable OOP-friendly structure: keep VS Code registration and prompt glue thin, move stateful contest behavior into the controller or focused helpers, and only introduce new classes when they own a clear long-lived responsibility.
- If you change a contributed command, menu item, view, or setting, update [package.json](package.json), [README.md](README.md), and any user-facing [CHANGELOG.md](CHANGELOG.md) entry that describes the change.
- Treat [README.md](README.md) as a VS Code extension README, not a generic library README. Keep the wording centered on extension usage and current capabilities.
- Keep output user-facing and concise in the `AutoJudge Contest` output channel and VS Code notifications.
- Start the development environment with `docker compose up -d --build` and run repository commands inside the `extension` service.
- Do not run `node`, `npm`, `npx`, or `vitest` directly on the host; use `docker compose exec extension ...` instead.
- When a task changes runtime behavior, add or update focused Vitest coverage when practical and validate with `docker compose exec extension npm test`.
- Never log passwords, bearer tokens, or other secret material to the output channel, notifications, tests, or persisted files.

## Runtime Behavior To Preserve

- The contributed commands are `autojudgeContest.loginTeam`, `autojudgeContest.logoutTeam`, `autojudgeContest.refreshTree`, `autojudgeContest.openContestDashboard`, `autojudgeContest.openProblem`, `autojudgeContest.submitActiveFile`, `autojudgeContest.exportPublicCases`, `autojudgeContest.openSubmission`, `autojudgeContest.openTeamStanding`, `autojudgeContest.openStandings`, `autojudgeContest.compareSubmissionOutput`, `autojudgeContest.showUnsolvedProblems`, and `autojudgeContest.showAllProblems`. Their titles and palette visibility live in `package.json`.
- Log In opens the web login on `autojudgeContest.webUrl` (`teams/login` with `client=vscode` and a fresh `state`) and waits up to 5 minutes for the `vscode://autojudge.autojudge-contest/auth` callback with a matching `state`. Only one login is pending at a time, and cancelling its progress notification ends it. No team code or password is typed in VS Code. The `autojudgeContest.baseUrl` setting is validated before the browser opens, so an invalid value fails first.
- A successful login redeems the one-time code and stores only the returned token in VS Code secrets. The team id is not stored in global state.
- Refresh, and the session restore at activation, load the current team, contest details, contest problems, and submissions, then update both sidebar views and the status bar. The activation restore is silent; a manual Refresh shows progress on the Contest Explorer and an error notification on failure. The extension activates on `onStartupFinished`, so this restore also runs after a window reload without the sidebar being opened.
- Only a `401` with `SESSION_ENDED` clears the stored session and returns the views to the logged-out state; the session-ended prompt is shown once until the next login. Any other restore failure, including a request with no response within 20 seconds, keeps the token and sets the views to the `offline` state with a Retry action. A failed standings refresh keeps the current snapshot and logs a warning. A `403` with `CONTEST_NOT_STARTED` keeps the token and shows the contest as not started; the standings refresh reloads the problems once the contest start time passes, so no manual Refresh is needed.
- Logged out, both views show a Log In welcome; while the first restore runs they show Loading. Logged in, `Contest Explorer` shows a contest header (name and phase: Running, Frozen, Ended, or Not started; time left is in the status bar) that opens the contest overview, then problems sorted by `order`, labelled by title alone (no `A.` letter prefix, matching the AutoJudge platform), and only that problem's submissions nested newest-first. A problem's balloon icon is filled once solved and a hollow ring until then; its description is only `Judging…` while a submission is pending or the attempt count while unsolved; a problem with a pending verdict opens expanded. A view-title filter toggles between all problems and unsolved problems only (kept in global state, mirrored in the `autojudgeContest.unsolvedOnly` context key); when it hides every problem an `All problems solved` note shows. Submission ages read `5 min ago`, then `1h20m ago` past an hour. `Standings` starts with a `Full standings` row (Open Full Standings writes the scoreboard table, with letter-keyed problem columns and a legend mapping each letter to the problem title, under `standings`), then shows teams ranked by solved problems, then lowest total time (ties share a rank), with your team highlighted, names over 24 characters shortened (full name in the tooltip), and `0 solved` for teams without a solve.
- Problem rows do not open on selection. The book action (Open Problem Statement) writes the statement as a Markdown page and opens it in the Markdown preview, while submission rows open the submission page directly on selection.
- Generated pages and compare files are written only under the storage root: `storageUri`, falling back to `globalStorageUri`, in the `contest-dashboards`, `problem-previews`, `submission-details`, `team-details`, `standings`, and `submission-output` folders, written by `src/workspace/contest-page-files.js`. Page and file names are sanitized for every platform (Windows reserved names get a `_` suffix). Only an explicit testcase export writes into the workspace.
- Submit Active File works from a problem row, the editor title bar (supported files only), or the Command Palette; the last two ask for the problem from unsolved problems only (an info message says when all are solved). It reads the active file, saves unsaved changes after a prompt, asks for an information-dialog confirmation unless `autojudgeContest.confirmBeforeSubmit` is off, merges the pending submission into the in-memory snapshot, reveals it in the explorer (expanding its problem while the view is visible), then polls until a final verdict. A problem the team has already solved is refused with an info message before the confirmation (for example, when chosen from its row), and a second submit is refused while the judge request is still in flight. Pending submissions are polled automatically after login, restore, and refresh, through one shared loop: one request per interval covers all of them, network errors are retried, and a submission still pending after the 2-minute window is checked again 30 seconds later. Verdicts show a notification with View Details, plus Compare Output when both expected and received output exist. The submission page heading is a `✓`/`✗` text mark (not an emoji) with the verdict and problem, followed by the full field list, and its diff (like Compare Output, received on the left) marks the team's output `-` and the expected output `+`. Generated pages contain no emoji.
- Open Team Details writes the team's details page (rank, solved count, total time, solved problems) under `team-details` and opens it. It does not write to the output channel.
- The status bar item is hidden when logged out. When logged in it shows the time left, your rank, and a judging count; it highlights the last 15 minutes of a running contest and opens the contest overview.
- `Standings` refreshes every 15 seconds while the view is visible and every 60 seconds while it is hidden, through the controller's contest-details refresh path (`GET contests/{contestId}`). Showing the view refreshes it at once. The Contest Explorer re-renders every 60 seconds while visible so submission ages stay current.
- Export Public Test Cases operates on the selected problem (or a quick pick) and writes `<problem title>-testcase-NN.in` and `.out` files numbered from `01`. The folder is the active file's folder, else the only workspace folder, else a folder chosen in a dialog. Existing files are replaced only after confirmation.
- The configured API base URL must support optional base paths; reuse [src/services/contest-api.js](src/services/contest-api.js) normalization instead of rebuilding URLs elsewhere. `baseUrl` and `webUrl` are read on each use. An invalid value raises an `INVALID_SETTING` error with an Open Settings action and does not block activation.

## Pitfalls

- Do not assume the public site URL and API URL are the same; the extension targets the API base URL configured by `autojudgeContest.baseUrl`.
- The login flow opens `teams/login` on the web URL, the browser hands back a one-time code, and `POST teams/session/redeem` exchanges it for the team token. Login and restore then load `GET teams`, `GET contests/{contestId}`, `GET contests/{contestId}/problems` (which may answer `403` with `CONTEST_NOT_STARTED`), and `GET submissions`. Submissions go to `POST problems/{problemId}/judge` with the Bearer token, and verdict polling reads `GET submissions`.
- `autojudgeContest.pollIntervalMs` is only for post-submit verdict polling; the standings cadence is fixed at 15 seconds while the Standings view is visible and 60 seconds while it is hidden.
- Public-case export does not read any testcase path setting. It writes to the active file's folder, else the only workspace folder, else a chosen folder.
